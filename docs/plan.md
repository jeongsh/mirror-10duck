# 🚀 오타쿠 커뮤니티 플랫폼 '씹덕' 프로젝트 플랜

## 📌 1. 프로젝트 개요 (Project Overview)
- **프로젝트 명:** 씹덕 (가칭)
- **핵심 가치:** 개인화된 캐릭터(Live2D) 상호작용과 서브컬처 커뮤니티의 융합, 그리고 C2C 창작 경제의 활성화.
- **최종 목표:** 사용자가 자신의 Live2D 캐릭터와 상호작용하며 커뮤니티 활동을 즐기고, 관련된 디지털 에셋을 거래할 수 있는 플랫폼 구축.
- **플랫폼 전략:** 웹(Next.js) 버전으로 MVP 우선 런칭 후, React Native(Expo)를 통한 모바일 네이티브 앱 확장.

---

## 🛠️ 2. 기술 스택 (Tech Stack)

### 2.1 프론트엔드 (웹 MVP)
- **Framework:** Next.js (App Router 구조 활용)
- **Language:** TypeScript (타입 안정성 및 유지보수성 확보)
- **Styling:** Tailwind CSS (빠른 UI 구현 및 일관된 디자인 시스템)
- **State Management:** Zustand (가볍고 직관적인 전역 상태 관리)

### 2.2 Live2D & 그래픽 처리
- **Rendering Engine:** PixiJS (WebGL 기반 2D 렌더링)
- **Live2D Integration:** `pixi-live2d-display` (React 환경에서의 Live2D 모델 제어 및 렌더링 최적화)

### 2.3 백엔드 & 데이터베이스 (BaaS)
- **Database & Auth:** Supabase (PostgreSQL 기반 DB, 사용자 인증, 실시간 데이터 구독)

## 📝 게시판 에디터·첨부·스티커 (플랜)

요약 표는 아래 상세 절과 동일한 방향을 한눈에 본다.

| 구분 | 현재 | 목표 |
|------|------|------|
| **에디터** | 임시 구현 (단순 입력 위주) | 정식 작성 UX + 첨부·삽입·미리보기 |
| **첨부** | 제한적 또는 미연동 | **이미지·영상** 업로드, 스토리지·정책, 본문 인라인 삽입 |
| **스티커** | 텍스트 토큰 저장 → 렌더 시 치환 | **이미지로 삽입·저장** (디시콘·캐릭터 스티커 모두 본문 속 이미지 블록) |

---

### 1. 목표와 참고 UX (디시인사이드·아카라이브)

- **벤치마크:** 디시인사이드·아카라이브류 **갤러리/게시판 글쓰기**에서 익숙한 패턴을 따른다 — 본문은 글 상자 흐름이 중심이고, **이미지·짤**은 본문 안에 **인라인 블록**으로 박히며, **영상**은 첨부 영역 또는 본문 삽입 후 플레이어로 재생된다.
- **스티커(디시콘/캐릭터):** 사용자가 보는 관점에서는 **“토큰 문자열”이 아니라 그 자리에 작은 이미지가 올라간 것**과 같아야 한다. 읽기 모드뿐 아니라 **작성 중에도** 미리보기 이미지가 보이는 것이 이상적이다.
- **원칙:** 모바일·데스크톱 모두에서 줄바꿈·정렬이 깨지지 않게 하고, 이미지·스티커는 **최대 너비·세로 정렬(`align-middle` 등)** 규칙을 통일한다.

---

### 2. 적용 범위

| 영역 | 요구 |
|------|------|
| **게시글 본문** | 이미지·영상·스티커 인라인 삽입, 제목과 분리된 본문 필드 유지 |
| **댓글** | 짧은 텍스트 위주이되, **스티커·이미지(및 필요 시 짧은 영상)** 정책을 게시글과 **동일한 렌더 규칙**으로 맞출지 여부를 결정 (권장: 스티커·이미지는 동일 파이프라인 재사용) |
| **피드 전용 글** | 크로스포스트·피드 작성 시에도 **동일 에디터 컴포넌트** 또는 동일 콘텐츠 스키마를 쓰면 유지보수 비용이 줄어든다 |

---

### 3. 콘텐츠 모델 (저장 형식) — 결정 사항

임시 기간에는 단일 `text` 필드에 마크업·토큰을 넣었을 수 있다. 정식 에디터에서는 아래 중 하나(또는 혼합)를 명시적으로 택한다.

| 방식 | 설명 | 장단점 요약 |
|------|------|----------------|
| **A. 블록 JSON** | `{ version, blocks: [ { type: 'paragraph' \| 'image' \| 'video' \| 'sticker', ... } ] }` 형태로 저장 | 구조화·검증 용이, XSS 면에서 안전하게 노드별 처리 가능. 마이그레이션 스크립트로 구 텍스트 흡수 가능 |
| **B. 제한 HTML** | 서버·클라이언트에서 허용 태그만 남기는 HTML 문자열 | 에디터 라이브러리와 궁합이 좋을 수 있음. **sanitize** 필수 (`<img src>` 화이트리스트 도메인 등) |
| **C. Markdown 확장** | 이미지 `![](url)`, 커스텀 확장으로 스티커 | 단순하지만 커스텀 노드 표현이 어색할 수 있음 |

**권장 방향:** 신규 글은 **A(블록 JSON)** 또는 **B(제한 HTML + 확실한 sanitize)** 중 하나로 통일하고, 기존 **토큰 문자열** 글은 읽기 시에만 변환(아래 10장)하거나 일괄 마이그레이션한다.

**메타데이터:** 각 이미지·영상 블록에는 가능하면 `width`/`height` 또는 비율, `storage_key` 또는 공개 URL, 스티커의 경우 `character_id`·`emotion_id`(또는 에셋 id)를 함께 두어 **통계·신고·재생성**에 쓸 수 있게 한다.

---

### 4. 작성 화면 UX

- **레이아웃:** 제목 입력 → 본문 에디터(필수) → 하단 또는 상단 **툴바**(이미지·영상·스티커·링크 등). 디시/아카라이브처럼 “본문 한 덩어리 + 첨부 버튼” 인지, Notion식 슬래시 메뉴인지는 팀 선호로 결정하되, **버튼 라벨은 사용자에게 직관적으로**(예: 사진, 동영상, 스티커).
- **커서 위치:** 삽입되는 미디어·스티커는 **현재 커서가 있는 줄**에 블록으로 들어가거나, 블록 에디터면 빈 단락을 이미지 블록으로 교체한다.
- **드래그 앤 드롭:** 데스크톱에서 이미지 파일을 본문으로 끌어다 놓으면 업로드 후 해당 위치에 삽입 (다중 파일이면 순서대로 블록 추가).
- **클립보드 붙여넣기:** 이미지 붙여넣기 시 업로드 트리거(용량·포맷 검사 후). HTML 붙여넣기 시 불필요한 스타일 제거(붙여넣기 sanitize).
- **업로드 중 상태:** 각 블록에 **진행률·스피너·실패 시 재시도** UI. 실패한 블록은 게시 전 삭제하거나 재업로드할 수 있게 한다.
- **미리보기 모드 (선택):** “미리보기” 탭으로 읽기 전용 렌더와 동일한 모습 확인. 최소한 게시 직전 확인 다이얼로그로 대체 가능.
- **이탈 방지:** 작성 중인 내용이 있으면 `beforeunload` 또는 라우터 가드로 **나가기 확인** (선택: 로컬 초안 자동 저장).

### 5. 이미지 첨부

- **지원 포맷:** 최소 `jpeg`, `png`, `webp`; 필요 시 `gif`(애니 GIF). **SVG 업로드**는 XSS 리스크가 있어 업로드 금지 또는 서버 변환 후 PNG만 제공 등 정책 결정.
- **용량·해상도:** 업로드당 최대 용량(MB), 긴 변 픽셀 상한(예: 8192 초과 시 클라이언트 리사이즈 또는 서버 리사이즈). 게시판별로 상한을 다르게 할지(운영 정책).
- **저장:** Supabase Storage(또는 동등) **비공개 버킷 + 서명 URL** 또는 공개 읽기 전용 URL. 경로 규칙 예: `posts/{postId}/{uuid}.webp`.
- **표시:** 읽기 시 **lazy loading**, `sizes`/`srcset`로 반응형(선택). 썸네일 변환(WebP)으로 트래픽 절감(후속).
- **대체 텍스트:** 접근성을 위해 `alt` 입력 필드 제공 여부(선택이지만 권장).
- **첨부만 모아 보기:** 디시 스타일 “첨부 파일 목록” 영역을 유지할지, 본문 블록만으로 충분한지 제품 결정.

---

### 6. 영상 첨부

- **소스 유형 (택1 또는 병행):** (1) 사용자 업로드 파일(mp4 등)을 스토리지에 저장 후 `<video controls>` 또는 HLS(후속), (2) **외부 임베드 URL**(YouTube 등)만 허용하고 본문에는 임베드 블록으로 저장.
- **용량·길이:** 업로드 영상은 용량·재생 시간 상한을 두어 스토리지·트랜스코딩 비용을 통제한다.
- **썸네일:** 첫 프레임 또는 별도 `poster` 이미지 업로드(선택).
- **자동재생:** 기본 **음소거 자동재생 금지**(브라우저 정책·UX). 사용자 클릭 후 재생.
- **인코딩:** 초기 MVP는 **단일 코덱(mp4 H.264)**만 허용해도 무방; 확장 시 서버 변환 큐.

---

### 7. 스티커 삽입 (캐릭터·디시콘형)

- **UX:** 툴바에서 “스티커” 클릭 → 피커(캐릭터별·감정별 그리드) → 선택 시 **본문에 이미지 블록 삽입**. 작성 중에는 토큰 문자열이 아니라 **미리보기 `<img>` 또는 동일 크기 플레이스홀더**가 보이게 한다.
- **저장:** 블록에 `type: 'sticker'`, `src`(CDN/스토리지 URL), 메타 `character_id`, `sticker_key` 등을 둔다. 스티커 에셋이 아직 없는 캐릭터는 피커에서 비활성 또는 “만들기” 유도(기존 스티커 제품 방향과 일치).
- **크기:** 인라인 작은 썸네일(고정 높이 px) + `vertical-align` 통일. 반응형에서 줄바꿈 시 깨짐 방지.
- **레거시:** 기존 `:sticker/...:` 텍스트는 **읽기 파이프라인**에서 블록 렌더로 치환하거나, 배치 마이그레이션으로 블록 JSON으로 변환(10장).

---

### 8. 업로드 파이프라인·보안·스토리지

- **인증:** 업로드는 로그인 사용자만; Supabase **RLS**와 **signed upload URL** 또는 서버 API에서 한 번 검증 후 업로드.
- **MIME 검증:** 클라이언트 확장자만이 아니라 **서버/Magic byte** 검증.
- **XSS:** HTML 저장 시 **strict sanitize**. 사용자가 임의 `script`·이벤트 핸들러를 넣지 못하게 한다.
- **URL 신뢰:** `<img src>`가 우리 스토리지·허용 CDN만 가리키도록 렌더러에서 검증.
- **레이트 리밋:** 동일 사용자·IP당 분당 업로드 수 제한(어뷰징 방지).
- **삭제:** 글 삭제 시 오브젝트 스토리지 정리(수명 주기 정책 또는 삭제 훅). 고아 파일 정리 배치(후속).

---

### 9. 읽기 전용 렌더링 (`RichContent` 등)

- **단일 진실 소스:** 게시·댓글 표시는 **동일 스키마 → 동일 렌더러**로 가져가 편집기 미리보기와 결과가 일치하게 한다.
- **성능:** 뷰포트 밖 이미지는 lazy; 긴 글은 블록 단위 가상 스크롤은 후속 최적화.
- **인용·링크:** 기본 링크는 `rel="noopener noreferrer"`, 외부 링크 정책(새 탭 등) 통일.

---

### 10. 호환성·마이그레이션

- **구버전 글:** 단일 텍스트 필드에 토큰만 있는 글 → 읽기 시 **토큰 정규식으로 블록 가상 변환** 또는 백그라운드 잡으로 JSON 마이그레이션.
- **버전 필드:** `content_version` 컬럼으로 렌더러 분기(예: `1` = raw token text, `2` = block JSON)를 두면 안전하다.

---

### 11. 접근성·모바일

- **키보드:** 툴바 버튼에 포커스 링, 단축키(선택).
- **스크린 리더:** 이미지 `alt`, 영상에 제목/설명(선택).
- **모바일:** 파일 선택·카메라 촬영 진입(플랫폼별), 가상 키보드가 올라올 때 에디터 영역 스크롤 유지.

---

### 12. 구현 우선순위 (권장 단계)

1. **콘텐츠 스키마 확정** (블록 JSON 또는 제한 HTML) + DB/API 필드 정리  
2. **이미지 업로드 + 본문 삽입** (가장 수요 높음)  
3. **스티커를 이미지 블록으로 전환** + 레거시 토큰 호환 읽기  
4. **영상** (업로드 또는 임베드 URL 중 MVP 범위 선택)  
5. **드래그앤드롭·붙여넣기·미리보기·초안 저장** 등 편의 기능 순차 적용  

위 세부 항목은 Phase 2의 「게시판 에디터·미디어·스티커 고도화」체크리스트와 대응하며, 구현 시 이 절을 하위 설계서로 삼는다.

### 💬 Phase 2: 핵심 기능 MVP 개발 (현재 진행)
핵심 가치인 '캐릭터와의 상호작용'과 '커뮤니티 소통' 기능을 구현하는 단계.

#### 2.1 Live2D 시스템 연동
- [x] PixiJS 기반 Live2D 모델 렌더링 로직 구현 (기본 모델 로드)
- [x] 마우스 커서 시선 추적 (Eye-tracking) 및 클릭 상호작용 이벤트 구현
- [x] 타이핑, 미활동(Idle), 접속 상태(로그인/로그아웃) 등 상황별 기본 애니메이션 연동
- [x] 사이트 알림(댓글, 쪽지 등) 발생 시 캐릭터 리액션 및 말풍선 UI 연동

#### 2.2 게시판 + 피드 하이브리드 시스템 (구현 난이도: 중~상)
- [ ] **닉네임·신원 뱃지 및 익명 작성 (플랜 연동)** — 위 「📛 닉네임·신원 유형 및 UI」 참고
  - [ ] 고정닉 / 비 고정닉 / 비 로그인 **뱃지 UI** (색·레이블·배치 통일)
  - [ ] 고정닉 **전역 유일** 닉네임 검증·예약(DB·정책)
  - [ ] 비 고정닉 **중복 허용** 데이터 모델·표시 규칙
  - [ ] 비 로그인 글/댓글: **일회용 닉네임·비밀번호** 입력 플로우, **IP(또는 대체 식별)** 표기 정책·저장
- [x] 사용자 인증 시스템 구현 (Supabase Auth 연동: 회원가입/로그인)
- [x] **독립 게시판(채널화) 시스템 구축**
  - [x] `boards` (채널) 테이블 설계 및 적용 (기존 카테고리 방식 대체)
  - [x] 동적 라우팅 적용 (`/board/[slug]`) 및 채널별 목록/글쓰기 UI 구현
  - [x] 기존 `posts` 테이블의 `category` 컬럼을 `board_id`로 마이그레이션
- [x] **피드(Feed) 도메인 구축**
  - [x] 유저별 팔로우 기반 타임라인 (Feed) 구성 및 RPC 쿼리 적용
  - [x] 유저 간 팔로우(`follows_user`), 게시판 팔로우(`follows_board`) 구현
- [x] **개념글(Hot) 시스템 연동**
  - [x] 개념글 등극 토글(디버그용) 및 UI 상태 연동
  - [x] 팔로우한 게시판의 개념글을 피드에 섞어 노출 (RPC 쿼리 적용 완료)
- [x] **피드 ↔ 게시판 브릿지 (Cross-post)**
  - [x] 피드 글을 특정 게시판으로 공유하는 모달 UI 및 API (`origin_post_id` 스냅샷) 구현
  - [x] 게시판 글을 피드로 스크랩(공유)하는 역방향 브릿지 UI 연동 완료
- [ ] **게시판 에디터·미디어·스티커 고도화** — 위 「📝 게시판 에디터·첨부·스티커」전절(§1 목표 ~ §12 우선순위) 참고 (디시인사이드·아카라이브 패턴)
  - [ ] 임시 에디터를 **이미지·영상 첨부**가 가능한 작성 UX로 교체·확장 (업로드 파이프라인·스토리지·본문 삽입)
  - [ ] 스티커: 텍스트 토큰 저장 방식에서 **본문에 실제 이미지가 박히는** 저장·렌더 모델로 이행 (피커 → 이미지 삽입, `RichContent` 등 연동)

#### 2.3 캐릭터-커뮤니티 연결 기능 (구현 난이도: 중)
- [x] 디시콘 스타일 캐릭터 스티커(인라인 임베드) 기능 구현 — **MVP: 텍스트 토큰 → 렌더 시 치환** (향후 「게시판 에디터·첨부·스티커」에 따라 **이미지 직접 임베드**로 이행)
  - [x] 본문 에디터에서 스티커 피커 열기 및 삽입 (`:sticker/{characterId}/{emotion}:` 토큰)
  - [x] 렌더 단계에서 토큰을 캐릭터 스티커 썸네일 컴포넌트로 변환 (`RichContent` + `CharacterSticker`)
  - [x] 모바일/웹 공통으로 깨지지 않는 스티커 크기·정렬 규칙 정의 (`inline-flex` + 고정 px + `align-middle`)
- **스티커 제품 방향 (정책·로드맵)**  
  - 캐릭터를 만든 직후에는 스티커가 자동으로 생기지 않는다. 사용자가 명시적으로 **「스티커 만들기」**를 실행했을 때만 스티커 에셋이 생성·연동된다.  
  - 이후 **AI 연동** 시에는 위 「만들기」 플로우 안에서 캐릭터를 참조해 **디시콘 스타일** 스티커가 자동 생성되도록 한다 (단일 일괄 자동 생성이 아니라, 사용자가 만들기를 택한 경우에만).  
  - **스티커 관리 페이지**를 추가해 보유 스티커·감정 세트·삭제·다시 만들기 진입 등을 제공한다 (Phase 3 범위로 상세 체크리스트 참고).
- [x] 캐릭터 리액션(좋아요 2.0) MVP 구현
  - [x] 글/댓글에 감정 리액션 6종 제공 (기쁨/공감/놀람/슬픔/웃김/응원)
  - [x] 리액션 집계 + 최근 반응자 캐릭터 스티커 썸네일 노출 (`post_reactions` 스냅샷 컬럼 활용)
  - [x] 텍스트 없이 누를 수 있는 '스티커 답글' (짧은 모션/아이콘 반응) 1차 버전 구현 (`CommentSection` 의 sticker-only 모드 + `ReactionBar`)

#### 2.4 AI 기반 캐릭터 상호작용 (구현 난이도: 중~상)
- [ ] 지시문(액션) 기반 1:1 롤플레잉 채팅 UI/UX 구현
- [ ] AI 프롬프트 연동을 통한 기본 페르소나 설정 및 대화 로직 구현
- [ ] (제타 벤치마킹) 캐릭터의 장기 기억(Long-term Memory) 시스템 기본 구조 설계
